# RAG_product


# Архитектура решения 
## Общая схема компонентов 

   * Search API (интернет-поиск) - StackExchange/Search API для поиска вопросов по StackOverFlow
   * FAISS(Векторная база) - для хэширования только полезных найденных ответов со StackOverFlow
   * LLM(ollama, Mistral AI, GPT-5)- модель, которую будем задавать системе для генерации ответа
   * LangChain - Библиотека, которую будем использовать для построения приложения(RAG) на основе LLM
   * Tg/Chatbot - для фронтенда чтобы можно было показывать результат работы


## Потока данных
### Шаг 1. Вход: вопрос / код / stacktrace
   *  На вход система получает текст вопроса, фрагмент кода или контекст, затем ассистент будет использовать базу на основе ответов поиска через StackExchange/Search API со Stack Overflow/Хабр и генерировать релевантные решения, реконмендации или рабочее решение.
   * Система распознаёт язык кода, выделяет:
      * Kлючевые слова и исключения 
      * Тип проблемы (сетевая, логическая, синтаксическая);
   
   ### Шаг 2. Формирование поискового запроса (Query Building)
* Пример:
   * site:stackoverflow.com "requests.exceptions.ReadTimeout" Python

   ### Шаг 3. Живый поиск (через интернет)
    * Система запрашивает Google/Bing/StackExchange API и получает:
         * заголовок,
         * URL,
         * сниппет,
         * дату,
         * рейтинг.

   ### Шаг 4. Загрузка и разбор страниц
   * Для топ 5–10 найденных URL:
      * скачать HTML,
      * извлечь текст,
   * выделить:
      * вопрос,
      * accepted answer,
      * код,
      * комментарии.

 ### Шаг 5. Эмбеддинг + Reranking найденных решений
   * разбить текст на чанки,
   * эмбеддинги (на лету),
   * reranker выбирает top-3 наиболее подходящих решения.

   ### Шаг 6. Генерация финального ответа
   * LLM получает:

      * вопрос пользователя,
      * 3–5 лучших найденных фрагментов,
      * ссылки,
      * примеры кода.

   ### Шаг 7. Отображение результата пользователю

   * Показывается:
      * текст ответа,
      * код с подсветкой,
      * ссылки на оригинальные статьи,
      * кнопки «Помогло / Не помогло».

   ### Шаг 8. Фидбек
   * Если пользователь нажал «Помогло»:
      * документ сохраняется в локальный векторный кэш (Faiss/Qdrant),
      * повышается рейтинг данного URL.
   * Если «Не помогло»:
      * не кэшируется,
      * система ищет альтернативные источники.



# Архитектура Backend RAG-системы
## 1. Presentation Layer — Слой представления
* Этот слой отвечает только за коммуникацию с внешними клиентами: Telegram-бот, Web UI, REST API.
### Основные задачи Presentation Layer:
* 1) Получение HTTP/JSON запросов
   * * Например:
     * POST /ask
   ``` json
   {
  "question": "Почему возникает ошибка requests.exceptions.Timeout?",
  "code": "requests.get(url, timeout=0.001)"
   } ```
* 2. Валидация входных данных
* 3. Преобразование DTO → внутренние модели
* 4. Вызов бизнес-логики (Application Services)
* 5. Преобразование ответа в JSON/HTML

## 2. Business Layer — Бизнес-логика
* Это основной логический слой, который реализует все шаги RAG-pipeline:

### Основные компоненты:
  * 2.1 QueryAnalysisService

      * Отвечает за анализ того, что ввёл пользователь:

         * определяет язык кода;

         * выделяет исключения и ключевые слова;

         * классифицирует тип проблемы;

         * формирует поисковый запрос.

   * Результат работы → объект SearchQuery

  * 2.2 SearchOrchestrationService (оркестратор поиска)

      * Это сервис, который:

         * получает поисковый запрос;

         * вызывает SearchGateway (инфраструктура) для поиска по интернету;

         * получает список заголовков и URL из SerpAPI/StackExchange;

         * вызывает PageFetcher (инфраструктура) для скачивания страниц;

         * передаёт эти тексты в RerankingService.
   
   * 2.3 RerankingService

      * Использует:

         * sentence-transformers embedding модель,

         * cross-encoder reranker.

      * Функции:

         * объединяет текстовые документы;

         * фильтрует нерелевантные;

         * сортирует по релевантности;

         * выбирает Top-K кандидатов.
   
   * 2.4 ContextBuilder

      * Создаёт финальный контекст для LLM, включая:

         * текст ответов,

         * фрагменты кода,

         * сниппеты,

         * ссылки на источники,

         * указания для LLM.

   * 2.5 AnswerGenerationService

      * Использует LLM (GPT-5 / Mistral / Llama) для генерации финального решения.

   * Функции:

      * создание prompt’а;

      * генерация ответа;

      * форматирование выхода.

   * 2.6 FeedbackService 

      * Принимает оценку "Помогло / Не помогло":

         * сохраняет в storage,

         * может триггерить улучшение ранжирования,

         * собирает статистику.

## 3. Infrastructure Layer — Инфраструктурный слой
* Это адаптеры: работа с API, хранилищами, внешними сервисами, файлами, кешами.

### Основные компоненты:
* 3.1 SearchGateway (SerpAPI / StackExchange)

* Реализует интерфейс ISearchProvider.

   * Задачи:

      * формирует HTTP-запросы для поиска;

      * парсит результаты: title, link, snippet, date;

      * обрабатывает ошибки, rate limits.

* 3.2 EmbeddingProvider

   * Оберта над SentenceTransformer:

   * загрузка модели

   * получение векторов

* 3.3 RerankerProvider

   * Адаптер для Cross-Encoder:

   * predict

   * batch reranking

* 3.4 LLMProvider

   * Адаптер для локальной или облачной модели (OpenAI, Mistral API).

   * Методы:

      * generate(prompt)

      * ограничение токенов

      * логирование

      * обработка ошибок

* 3.5 CacheProvider

   * SQLite как долговременный кэш страниц (перед повторной загрузкой)

   * Faiss/Qdrant как опциональный векторный горячий кэш (для производительности на популярных запросах)
